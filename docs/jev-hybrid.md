# 2026-09-28: 局所相談と移動継続

前回の30分ログでは、Opus呼び出し81回中71回の完了応答が全体計画の再検討だった。
ビルドと装備が変わっていないエリア移動・敵の変化・継続許可の終了は、
`decision_scope: local` で現在の目標、戦術、継続条件だけを更新する。
既存の戦略と記憶は保持し、スキル購入一覧は入力から外す。現在の能力・所持品・
状態異常・観測履歴は残す。安全な局面はmedium、敵や危険がある局面はhighを使う。
初期ビルド、成長、装備、クエストに関する判断は全体相談を維持する。

継続許可の手数切れでも、HP満タン・可視敵なし・未知または危険な状態異常なし・
ビルドと目的が不変・同じエリアの既知の未到達目的地・被害と操作失敗なしなら、
承認済み目的地への自動移動へ戻せる。目的地に到達済みなら局所相談する。
この更新で被害履歴や上位判断時の観測基準はリセットしない。

`derived.survival` は同じエリアの直近の操作で観測された最大HP減少、現在HPとの比較、
公開説明に回復効果が記載されたアイテムの操作候補を示す。減少量は被害の上限ではなく、
候補の提示も自動使用の承認ではない。副作用と現在の危険をOpusが比較する。
直近の減少量以上のHPが残っていない敵遭遇中は、2回以上被害を観測した位置への移動を
Opusが最初の行動に選んでも実行せず、別の行動を要求する。未訪問の退避先の安全性まで
保証する判定ではない。

保存済みの完全な計画の形式は維持する。新しい局所応答はCLIのJSONスキーマで9フィールドを
要求し、実行前に既存計画へ統合して検証する。応答の生成元は`Models.claude`のみで、
通常の全体応答・従来の限定応答・保存済み計画を引き続き受け付ける。
過去ログの境界条件6例、実行ループ、入力と出力の契約を回帰テストにした。

## 2026-09-28: 地形と探索履歴の共有

`observation.spatial` を任意の追加項目として導入した。現行の送信元は
`ObservationBuilder.Build` で、旧台帳・治具・古いmodの観測には必須化しない。
既存フィールドと保存済み計画の形式は維持する。

- visibility は v（可視・探索済み・明るい）、m（探索済みだが現在は観測外）、u（未探索）。
- terrain は ?（不明）、.（可視の静的障害物なし）、#（可視の固体）、+（扉）、~（開いた液体）、< >（階段）。
- 見えていないセル内の物体は調べない。可視の物体だけから分類し、混乱中は地形を不明にする。経路探索やセル全体の通行判定で隠れた障害物を取得しない。
- 地形名は足元と隣接セルの可視物体を各4件・各256文字まで。生物は既存の座標付き観測を使用する。
- . は通行や安全の保証ではない。隠れた対象・移動効果・液体や扉の相互作用は別に扱う。

ハーネスは最大32ゾーンの観測地形、到着回数、直近32件の移動失敗を保持し、
`derived.mapping` を両モデルへ同じ内容で渡す。ゲームの巻き戻し時には破棄する。
これは走行中の記憶で、別プレイへの継承はしない。訪問回数は観測できた到着地点に限り、
自動移動の中間セルを推測しない。未知領域に隣接する到達可能な地点と既知地形上の
経路距離を示す。既知8方向の接続が1以下で未知領域に接しない地点を行き止まり候補とする。
過去の移動失敗は永久的な通行禁止にはしない。現在の地形変化で直前のブロックを再評価する。

可視の固体への移動を候補から除外し、明示された通路・階段なら表示記号が特殊でも
自律移動の対象とする。扉・液体・不明地形はこの拡張で自動承認しない。
ゾーン探索では小さな座標目標の更新を繰り返す代わりに、target:null・mode:exploreの
目的単位の許可を優先するよう上位へ指示する。承認済みの戦闘位置へ到着しただけでは、
その敵が近くに残っている限り戦闘許可を終了しない。建物内の複雑な接続や動的な障害物、
危険地点の解除、並行する上位推論は引き続き別の課題である。

## 2026-09-29: 自動探索の利用可否と制約付き経路

`derived.navigation` をJevとOpusの両方に渡す。`explore` / `goto` の `available` と
`reasons` は、候補から消えた場合にも残る。可視敵、危険・未知効果、HP下限、ワールドマップ、
移動方向制約、除外地点、目的地の未指定・未探索・到達済みを区別する。利用可能という情報は
実行承認ではなく、実際に選択できるのは現在の候補IDに限る。

除外地点・方向制約がない安全な状況では、従来のゲーム標準 `explore` / `goto` を使う。
標準マクロには禁止地点を渡せないため、制約がある場合はそのマクロを引き続き提示しない。
代わりに、有効な `autonomy` がある探索・移動計画では、共有済み地形の通路・階段を使い、
除外地点・可視生物・扉・液体・不明地形を避ける経路を計算する。目的地指定があればその地点、
指定がなければ到達可能な未踏境界を選ぶ。最初の移動候補の `navigation` に目的地と経路を付け、
Jevがこの候補を選ぶと、最初の一歩を含む最大12歩を実行器が継続できる。

この経路は標準のauto exploreではなく、通常の `move` を1歩ずつ発行するハーネス側の処理。
毎歩の観測・結果・台帳記録を保持し、次のセルが現在可視の通路・階段であることを確認する。
計画・ゾーン・seq・現在位置が変わった場合、敵・被害・危険効果・モーダル・移動失敗が発生した場合、
または既存の任務許可境界を超えた場合は継続しない。モデルに渡す候補と最終実行検査にも除外条件が残る。
12歩の終了後は再選択する。実行途中の経路は保存計画や別セッションへ持ち越さない。

制約下で指定目的地への既知経路が見つからない場合は、`navigation_target_unreachable` で局所相談する。
これはゲーム世界で絶対に到達不能という断定ではなく、現在の観測と許可条件では経路を作れないという報告。
過去の被害地点を自動解除する変更は含まない。既存のワイヤープロトコル・ゲーム側mod・保存計画の形も変更しない。


同日の診断走行run9では、レベルアップ前後のキャラクター全体と古い会話本文が重複し、
JevがHTTP 400 `max_tokens_exceeded`を返した。公式の[モデル仕様](https://docs.typesafe.ai/models)は、
stateと最長の問いを合わせて32k tokensを上限としている（2026-09-28確認）。
Jev向けの履歴は8操作の結果・HP変化を保持し、全文メッセージと詳細変更は最新操作のみ、
過去イベントは危険結果とゾーン移動を16件、会話履歴は直近2件へ整理した。
現在の観測、地形、探索記憶、危険地点、被害集計、許可条件は省略しない。
上位へ渡す履歴は従来どおり保持する。巨大な所持品説明など、任意の最大長入力について
上限内を保証するトークナイザ検査は今回の変更には含まない。

## 2026-09-29: run10で観測した回復・追跡・通信失敗

`tactics.recovery_hp_target` は回復を完了とするHP。`mode:recover` で、休息地点へ到着済み
（targetがnullまたは現在地）、可視敵なし、未知・危険効果なしの場合、目標までnative restを
繰り返す。現在の最大HPを超える値は最大HPまでとする。回復地点への到着自体では許可を終えない。
実行側が休息を選ぶため、休息のたびのJev呼び出しとOpus相談を要しない。許可手数、被害、
成長・クエスト変更など既存の確認は維持する。HPが上がらなくても、成功してターンが進んだ
休息の反復は移動の停滞と扱わない。回復完了後は`recovery_complete`で次の目的を局所相談する。
回復未完了・危険なしでの移動再開は、Jevの確率や上位の選択にかかわらず拒否する。
危険出現時の退避まで妨げるものではない。休息地点への移動がまだ必要な旧計画も維持する。

このフィールドの生成元は`Models.claude`の全体・局所応答。両スキーマのtacticsへ追加した。
従来の限定応答は保存済みtacticsを保持し、playの保存・resumeはそのまま扱う。
旧計画とテスト用writerは項目を省略でき、省略またはnullはHP満タンを目標とする。
旧形式を必須項目不足で拒否しない。run8〜10の保存済み228計画が検証を通ることを確認した。

旧`continuation`の追跡判定は、名前が一意の敵について、前回承認時と現在それぞれの
プレイヤー位置からの距離を比較する。プレイヤーと敵が共に動いて距離を保つ場合に
許可を失効させない。名前が重複して個体の対応が曖昧な場合は従来の保守的な判定を維持する。
新たな隣接、実際の距離悪化、追加敵、既存の被害上限、操作失敗、経路逸脱、期限は再相談する。
敵が静止していても、プレイヤーの移動で新たに隣接した場合は再評価する。

JevのHTTPクライアントはプレイヤーの実行中に再利用し、終了時に閉じる。
connect/read/write/poolの個別タイムアウトを撤廃した。プレイ全体の実行期限とキャンセルは維持する。
[公式API](https://docs.typesafe.ai/api)と[公式SDKの再試行設定](https://docs.typesafe.ai/sdk/python/api/retries)
を参照し、一時的な接続エラー、408、429、5xx（529を含む）は同じ入力で最大2回再試行する。
Retry-After／retry-after-ms（秒・ミリ秒・HTTP日時）を尊重し、指定がなければ0.5秒から倍増する
待機にジッターを加える。これは推論の再送であり、ゲーム操作の再送ではない。
操作直前のseq・観測ハッシュ照合は引き続き必須で、通信待ち中に状態が変われば実行しない。

再試行を使い切った場合だけOpusへ代行する。成長等の未処理事項がなければ局所相談にし、
既存ビルド戦略の再生成を避ける。400、401、403、422等や不正な成功応答は原因を記録して停止する。
同じ不正入力や認証情報で再試行しても修復できず、ゲームの上位判断にも解決させない。

`jev-00001.json`等に、入力サイズ・ハッシュ、試行番号、各通信段階の時間、HTTPステータス、
必要な応答ヘッダー（request-id、cf-ray、retry-after等）、エラー本文の先頭2048文字、再試行待ちを保存する。
Authorizationを含む内部trace情報は保存せず、APIキーを伏せ、ファイルは0600で作成する。
キャンセル時にも診断を残す。HTTP応答本文は1MiBを上限として読み取る。
